# CourseBookAgent 开发与协作协议

> 本文档是项目文档系统中的开发协议。它不是产品需求，也不是代码百科；具体技术事实以 `ARCHITECTURE.md`、`WORKFLOW.md` 和 API 文档为准。

## 1. 接手顺序

新 AI 或新队员开始任务时，按以下顺序建立事实：

1. 读根目录 `AGENTS.md`，确认入口、命令和边界。
2. 读 `docs/PRODUCT_HANDOFF.md`，确认产品主线和比赛口径。
3. 读 `docs/ARCHITECTURE.md` 与 `docs/WORKFLOW.md`，确认当前实现，而不是根据旧对话猜测。
4. 读 `docs/ISSUES.md`，只把其中仍与代码和实验结果一致的条目当作待办。
5. 需要接口时读 `docs/API.md`；需要智云细节时读 `docs/API_ZHIYUN.md`。
6. 涉及已有决策时读对应的 `docs/decisions/` 文档，不能静默推翻已接受决策。
7. 开始编码前检查 Git 状态、当前分支、最近提交和本机 `data/` 产物；运行时数据不等于仓库事实。

## 2. 产品与范围

- 主产品是“智云课堂课程 → 结构化课程教辅书”。
- 当前对外叙述以教师为主：沉淀课程资产、生成讲义草稿、支持教师审核；学生复习是第二使用场景。
- 典型流程是：选课 → 获取讲次和字幕 → 显示生成过程 → 阅读教辅 → 导出 Markdown。
- 不要擅自把项目改造成通用聊天机器人、全校学习平台、个性化学习画像系统或自训垂直模型。
- 新需求必须说明它如何改善成稿质量、生成可靠性、用户可见性或比赛演示；不能只因为技术上有趣就加入。
- 先完成一讲可供教师判断的效果，再扩展到全课程；不要用预生成成品掩盖实时生成链路的问题。

## 3. 当前协作分工

会议已确认三条独立工作线：

| 工作线 | 目标 | 主要交付物 |
|---|---|---|
| 前端交互与引导 | 让用户知道系统正在获取、处理和生成什么，避免像开发者工具或卡死 | 可见的任务状态、阶段信息、失败提示、恢复入口和演示流程 |
| 生成稳定性 | 处理超时、坏 JSON、单讲失败、重试、取消和中途恢复 | 可复现测试、错误隔离、阶段性落盘、恢复机制和状态契约 |
| 输出质量 | 降低 AI 味，改善章节结构、衔接、例子和可复习性 | prompt/workflow/few-shot 调整、样例对照、质量评价记录 |

三条工作线可以并行，但涉及共享数据模型、任务状态、持久化目录、生成流程或比赛叙述的改动，必须先在任务说明或 ADR 中写清影响，不要各自重写基础结构。

## 4. Git 与提交

- 当前基线：`main` 与 `origin/main`，最近已知提交为 `90b38a9`；接手时仍须重新检查。
- 每个独立功能从独立分支开始。分支命名可用 `feat/<topic>`、`fix/<topic>`、`docs/<topic>`。
- 改动前先检查 `git status`，不要覆盖队友未提交的修改。
- 小步提交，每个独立功能点一个 commit。提交信息使用英文类型前缀：`feat: ...`、`fix: ...`、`docs: ...`、`test: ...`、`refactor: ...`、`chore: ...`。
- 分支 push 后先检查 diff、测试结果和文档，再由负责人合并；不要直接在 `main` 上堆叠未审查的大改动。
- `data/`、`.env`、`.venv/`、`frontend/node_modules/` 和 `.pi-subagents/` 被忽略，不提交凭据、原始字幕或本机生成产物。

## 5. 验证协议

后端改动至少执行：

```bash
uv run python -m unittest discover -s tests -v
```

前端改动至少执行：

```bash
cd frontend
npm run build
npm run lint
```

涉及 API 或用户流程时，还要启动后端和前端，使用真实浏览器走一遍相关流程。验证要记录实际结果，不把“代码看起来合理”当作端到端验证。LLM、智云或本机缓存不可用时，必须明确区分“离线确定性测试通过”和“真实外部链路未验证”。

生成稳定性问题的验证顺序：

1. 先做最小可复现测试，确认任务是否真的阻塞。
2. 分别记录 LLM 请求、超时/重试、JSON 解析、章节完成计数和异常传播。
3. 再检查 `generation_lock`、章节并发、后台任务生命周期和前端轮询。
4. 只有证据支持时，才把现象归纳为根因。

## 6. 文档同步

- 产品范围、比赛口径变化：更新 `PRODUCT_HANDOFF.md` 和 `COMPETITION.md`。
- 模块、数据模型、接口变化：更新 `ARCHITECTURE.md`、`API.md` 或 `API_ZHIYUN.md`。
- 工作流、缓存、恢复、质量策略变化：更新 `WORKFLOW.md`。
- 已接受的架构或范围决策：新增编号连续的 `docs/decisions/NNN-*.md`。
- 当前问题、已验证状态和残余风险：更新 `ISSUES.md`，不要保留与实际代码冲突的“已完成”描述。
- 修改代码时同步修改受影响的文档；只改文档时也要说明依据是代码、测试还是实验产物。

## 7. 不确定时的处理

- 先查代码、测试、Git 历史和本机实验记录，再提出判断。
- 不把旧会话、旧产物或旧问题清单当作当前事实。
- 架构方向、破坏性数据迁移、比赛定位和多人协作边界不确定时，先停在方案确认，不直接重写。
- 失败结果要保留复现条件和证据；不要用预生成样例、启发式回退或前端隐藏错误来冒充问题已解决。
