# 拆解设计（DECOMPOSITION）

> 这份文档回答：**"课程资料 → 教辅书"这条流水线为什么这样拆**。
> 每一步记录四件事：解决什么问题、契约（输入输出）、判断标准（在 lab 里看什么）、置信度。
>
> 置信度标记：
> - 🟢 **策略级**：已确认的设计决策，不应被实践轻易推翻；
> - 🟡 **参数级**：当前假设，跑过实验后再修正。
>
> 与 `docs/WORKFLOW.md` 的分工：本文档是"为什么这样拆、怎么判断对错"；WORKFLOW.md 是"实现现状"。

> 2026-10-09 状态提醒：已跑通12章真实成书；本文中的全书质量检查、自动回炉等仍须区分设计与实现。当前实际执行在章节阶段检查后合成/渲染，没有独立全书自动审稿闭环，见 CURRENT_STATUS.md / WORKFLOW.md。

## 0. 工作方法：为什么逐阶段跑

**"怎么拆"本身是假设，不是既定设计。** 每个阶段的产物是一个中间表示（description → 规划/Tag → 章节草稿 → 成书），拆解是否合理，判断依据是中间表示：信息有没有保真传下去、粒度对不对、有没有丢东西。

因此：

- 不一口气跑到底。错误会被后面的阶段掩盖或放大；跑到底只会在成书时发现烂，无法定位哪一步拆错。
- 每个阶段的产物必须**可观察、可由产品负责人判读**（不读代码也能判断好坏）。
- 跑一步 → 看产物 → 判断这一步的拆法对不对 → 对了进下一步；不对就改这一步的**定义**，而不只是调参数。
- 实验台：`scripts/lab.py`（CLI）与 `/api/product/snapshots/{id}/lab/*`（API）。每阶段独立缓存、可 `--force` 单独重跑。实验代码不进前端。

实例：describe 曾产出垃圾（topic=日期、知识点=水词），正是因为逐阶段跑才定位到"transcript 走启发式跳过 LLM"这条错误拆法；若直接跑到底只会得到一本烂书，然后在 prompt 上瞎调。

## 总流程

```text
获取资料 → parse → snapshot          （数据侧：把资料变成可复现的输入）
   ↓
describe → plan → assemble           （生成侧上游：语义化 → 规划 → 装配）
   ↓
generate → synthesize → quality → render  （生成侧下游：成书）
```

## 数据侧

### 1. 获取（上传 / 智云 / 学在浙大）

- **解决什么问题**：把散落的课程资料收进一个资料库（dataset）。
- **契约**：任意载体（transcript、PPTX、PDF、DOCX、MD、TXT）→ 资源（resource）+ 版本（revision）。上传是主路径；智云/学在浙大是浙大学生的便捷接入。
- **判断标准**：资料进入资料库后可预览、可解析。
- **置信度**：🟢 产品主线（学生上传为主）。

### 2. parse

- **解决什么问题**：把载体变成机器可读的结构化文本，供下游统一消费。
- **契约**：revision → `ParsedResource`（kind / title / units / raw_text）。纯解析，不做理解，不调 LLM。
- **判断标准**：解析文本可读、无乱码；坏载体（扫描件、缺页）在此暴露而不是在生成时才炸。
- **置信度**：🟢。

### 3. snapshot（输入快照）

- **解决什么问题**：锁定本次生成使用的资料版本，保证同一快照可复现、可对比。
- **契约**：dataset + 一组 revision_id → `snapshot_id`。生成运行绑定 snapshot，不绑定"当前资料库状态"。
- **判断标准**：同一 snapshot 重跑得到同一输入；资料更新后应建新快照而不是污染旧快照。
- **置信度**：🟢。

## 生成侧

### 4. describe（逐份资料语义化）

- **解决什么问题**：主 Agent 面对的是信道问题——N 份资料原文总量远超它一次能读的量，但必须基于全部资料做全局规划。description 是每份资料**面向规划决策的有损压缩**：只保真规划需要的信息（覆盖什么主题、什么粒度、独特价值、怎么用），不复述原文。
- **契约**：`ParsedResource` → `ResourceDescription`，核心是 `body`——一份固定五栏目的 Markdown：

  | 栏目 | 内容 | 点数 |
  |---|---|---|
  | `## 形态与性质` | 资料类型（讲授转写/课件/讲义/论文/大纲/习题…）、形式特征、来源与载体质量（噪声、乱码、缺失）、体量 | 3–5 条 |
  | `## 内容板块` | 按出现顺序分块：主题名 + 2–4 句（讲了什么、怎么讲/怎么呈现）+ 篇幅占比；覆盖全文，占比合计 ≈100% | 数量由内容定，一般 4–8 块 |
  | `## 独特价值` | 只写这份资料独有的：讲解、点评、案例、推导、直觉解释；每条注明出自哪个板块 | 3–6 条 |
  | `## 术语、关键词与可用性` | 术语/人名/缩写的规范写法（载体有误写给「资料写法 → 规范写法」对照）；可跳过/压缩的部分、不完整处 | 术语 5–15 条 + 可用性 2–5 条 |
  | `## 章节归属建议` | 适合进哪些主题章节、角色（主干素材/案例/附录），每条带一句理由；是建议不是结论 | 2–5 条 |

  配套规则：
  - **载体无关**：五个栏目对任何载体都成立；ASR 错字、OCR 乱码、幻灯片缺页只是"载体质量"的实例，不是独立栏目。
  - **忠实性**：只写资料中出现的内容，禁止外部知识补充；听不清/矛盾标 `[待核]`；数字、人名、结论必须来自原文。
  - **术语表是唯一直接进正文生产的原料**：下游写书统一术语靠它。
- **判断标准**：① 五栏目齐全；② 内容板块覆盖全文（不挑重点）；③ 独特价值真"独特"；④ 术语对照真实存在（抽 2–3 条回原文核对忠实性）；⑤ 形态判定准确（讲授/汇报/实操/文献）。
- **置信度**：
  - 🟢 transcript 必须走 LLM 语义化（启发式只做 LLM 失败的降级 fallback）；
  - 🟢 五栏目结构、载体无关框架、忠实性规则；
  - 🟡 长度：规范初稿 1200–2500 字，实测 3000–4800 字信息密度更好，**已确认接受约 3000 字**（2026-09-27）；
  - 🟡 章节归属建议字段：保留（带理由、标注为建议），但 plan 不得被它锚定——plan 必须自报规划依据。

**已验证事实（2026-09-27）**：snap_810cda9ba190（《数据科学与心理学研究》16 份真实 ASR 字幕）describe 全量通过：16/16 五栏目完整、零降级；产物见 `data/intermediate/descriptions/`。

### 5. plan（主 Agent 全书规划）

- **解决什么问题**：把 N 份 description 合成一本书的结构——章节、风格、每份资料的归属（Tag）。这是唯一做全局判断的地方。
- **契约**：全部 description（含 body）+ 课程元信息 → `BookPlan`：章节列表（`ChapterInstruction`，含 must_cover / section_plan）、`resource_tags`（revision → 章节列表 / `__global__` / 无 Tag）、全书风格（components、writer_system_prompt、canonical_glossary）。
- **关键设计**：
  - 章节是书籍主题，不是讲次；章节数由主题决定，不由资料数决定；顺序由教学逻辑决定。
  - **plan 纯看 description**，不读原文。粒度问题在 describe 层解决；一旦允许 plan 读原文，context 预算问题回归且错误无法定位。
  - Tag 是上下文归属（chapter / global / 无），不是流程控制。无 Tag 资料不进本次生成。
- **判断标准**：① 章节标题是主题不是"第 X 讲"；② 多讲合并、单讲拆分确实发生（对照 16 份的题材分布）；③ Tag 归属有道理（资料进的章和它的内容板块对得上）；④ 风格与深度设定像"教辅书"不像"摘要拼接"。
- **置信度**：🟢 章节≠讲次、plan 纯看 description；🟡 "规划依据自报"（每章依据哪份资料的哪些板块）尚未实现，先跑基线观察再决定是否加。

### 6. assemble（按 Tag 装配上下文）

- **解决什么问题**：把规划落实为每个章节 Agent 的输入，纯函数、零 LLM。
- **契约**：`BookPlan.resource_tags` + 资料 → 每章 `ChapterContext`（chapter_resources + global_resources）。global 资料进每章；无 Tag 资料不出现。
- **判断标准**：每章上下文和它的 Tag 一致；不漏不错装。
- **置信度**：🟢（纯确定性逻辑，测试覆盖）。

### 7. generate（分章撰写）

- **解决什么问题**：一章一个章节 Agent，按 `ChapterInstruction` + `ChapterContext` 写出完整章节。
- **判断标准**：章节像书的一章（有结构、有推导、有例题），不像讲次摘要；用了 Tag 进来的资料而不是泛泛而谈。
- **置信度**：🟡（prompt 与 few-shot 是主要调优面，逐章实验迭代）。

### 8. synthesize（全书合成）+ 9. quality（质量检查）+ render

- **解决什么问题**：合成全书（衔接、统一风格）；检查质量；渲染 Web / Markdown。
- **quality 的设计立场（2026-09-26 讨论）**：
  - 🟢 **机械门禁是危险的**——AI 产品避免用确定性规则判断内容质量（"结构完整""重复度"这类根本不是机械可判的）。质量判断交给 AI。
  - 🟡 **检查分层待定**：不逐步加 LLM 检查（烧 token、且逐步检查只能发现问题不能定位问题）；倾向"语义检查集中在输出端一次 + 审稿有权回炉重跑某章/重回 plan"，回炉轮数设上限防死循环。质量检查角色可以拥有主 Agent 的规划权（回炉重规划），细则待实验。
- **判断标准**：成书通读像一本可复习的教辅书；AI 味低；章节间衔接成立。

## 开放问题（待实验回答）

1. plan 的"规划依据自报"要不要进契约（对照基线输出再定）。
2. quality 的回炉机制：审稿角色的权限边界（重生成单章 / 重回 plan / 剔除资料）、回炉上限。
3. describe 的格式小漂移（个别份用 ① 不用 1.）是否值得加修复约束。
4. **【待办】主 Agent 只读取原文工具**：规划时对某份资料不确定可拉原文/片段核实，有限轮次（如最多 5 次 fetch）。是"关键资料全量注入"的按需版，复杂度低、不破坏拆解。触发条件：plan 因 description 信息不足出错时。
5. **【待办】关键资料全量注入**：决定权不给 description（有损压缩产物决定谁重要是循环论证），只能人工标记"重点资料"或确定性规则（类型=大纲/教材→注入），配套预算核算。触发条件同上（must_verify 里的数字矛盾是前兆信号）。
6. **明确不做**：主 Agent 自主派任务 / 开放式连续对话（agent 循环）——破坏错误可定位性、违反"主 Agent 不做流程编排器"、token 不可控。返工需求由审稿回炉机制表达；人机"对话式改规划"是产品层的"带反馈重规划"，不需要 agent 自主对话。
